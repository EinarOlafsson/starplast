================================================================================

STATE (measured 2026-08-11, do not take on trust -- re-measure)
    The registry's paths are relative to the repo's PARENT directory, not the
    repo. From inside the working copy, 1 of 16 registry paths resolves. The
    raw tree lives at /mnt/firecuda2/Claude/toxoplasma_projects/datasets and is
    NOT committed and NOT inside the repo.

    So `build_graph.py` works from exactly one directory on one machine and
    nowhere else, and nothing says so. That is a reproducibility problem for a
    PLOS ONE submission specifically: a reader who clones the repo and follows
    the instructions gets 15 missing files and no explanation.

    What IS committed: data/ -- 17 files, 17 MB, the built cache. The
    application itself already needs nothing else. The gap is the REBUILD path,
    not the run path.

USER INSTRUCTION (2026-08-11)
    "if possible set it up so starplast is standalone and doesnt need external
    data, or that the external data it needs is downloaded automatically by the
    application if it can't find it upon installation"

    Both halves, in that order of preference:
      1. standalone for RUNNING       -- already true via the committed cache;
                                         make it verifiably true and keep it so
      2. automatic for REBUILDING     -- fetch what is missing, on demand,
                                         without the user finding files by hand

WHAT TO DO
    - starplast/paths.py: one resolver every module goes through. No module
      opens a relative path directly ever again -- that is what produced a
      layout only one machine satisfies.

      Resolution order, each step reported so the user can see which one fired:
        1. $STARPLAST_DATA                    explicit override wins
        2. <repo>/datasets                    the layout a clone implies
        3. <repo>/../datasets                 the layout that exists today
        4. platform user cache dir            where downloads land
        5. download from the registry URL     into (4), then use it

    - datasets.ensure(key) -> local path. Downloads if absent, verifies size,
      records a checksum on first fetch so a silently changed remote is caught.
      Registry entries already carry `url` where one exists.

    - For entries with NO url (curated tables, files only in a paper's
      supplement): publish the raw tree as a HuggingFace dataset and give those
      entries that URL. hf_publish.py already exists. Until that is done, the
      resolver must say exactly which files it cannot fetch and why, rather
      than failing on open().

    - A first-run check on import: verify the committed cache is present and
      complete, and if it is not, say what to do in one sentence.

    - The packaging specs must bundle data/ -- an installer that ships an app
      which then cannot find its own cache is the same bug wearing a different
      hat.

HOW TO KNOW IT WORKED
    Clone into a brand new directory, `pip install -e .`, run `starplast`, and
    it opens the map with no manual step and no network.

    Then delete the raw datasets tree entirely and run build_graph: it fetches
    what it can, names precisely what it cannot, and does not traceback.

TRAPS
    Do not make the run path depend on the network to prove the download path
    works. Running offline is the stronger property and must not regress.

    A checksum recorded on first fetch pins whatever was fetched, including a
    corrupt download. Verify size and parseability before recording one.

DONE -- 2026-08-12
================================================================================

paths.py resolves both roots in one place. Nothing opens a relative path any
more, which is what produced a layout only one machine satisfied.

MEASURED BEFORE AND AFTER
    registry paths resolving from the repo     1 of 16   ->   23 of 26
    (the three that remain are genuinely absent from this machine and are
     named rather than counted)

THE CACHE MOVED INSIDE THE PACKAGE
    <repo>/data -> starplast/data. As built before, an installed wheel unpacked
    a generic top-level `data/` into site-packages -- collidable with any other
    package doing the same -- and the package-data glob matched two extensions
    without recursing, so it silently omitted all three toxodb_*.tsv identity
    tables and the hf_release subdirectory. The registry already recorded the
    identity table as starplast/data/, so the layout it described and the layout
    on disk had drifted apart.

VERIFIED THE WAY THE CLAIM IS STATED
    Built a wheel, installed it into a clean environment, ran it from /tmp with
    no repository, no configuration and no network: 8,140 genes, 12 edge types.
    Running was already standalone; the REBUILD path was not, and that is what
    the resolver fixes.

DECISIONS WORTH KEEPING
    An explicit override is honoured absolutely, even when it points at nothing.
    It used to fall through to the next candidate, so a mistyped
    $STARPLAST_CACHE silently gave a different cache than the one asked for --
    precisely the failure this module exists to prevent. Wrong and loud beats
    wrong and quiet. A test caught that; the first version had the bug.

    find() searches EVERY root rather than stopping at the first that exists,
    because half the files moved to datasets/<level>/<type>/<PMID>/ and half did
    not, and stopping early silently lost the CRISPR screens once already.

    datasets.ensure() refuses what it cannot honestly get: a landing page is not
    a file, and an HTML error page served with status 200 is the normal case
    rather than the odd one, so size never proves a file arrived.

TOXODB ROUTE ADDED -- 2026-08-12
    `toxodb_identity` was reported as unfetchable because its URL looks like a
    landing page. It is not: the tabular report is a POST with a JSON body, and
    fetch_names has been doing it all along. ensure() now knows that route, so
    the count of datasets a clean machine cannot rebuild drops from 13 to 12.

THE HUGGINGFACE MIRROR IS A DECISION, NOT A TASK -- 2026-08-12
    Staged and verified locally, NOT uploaded. The account is authenticated, so
    this stopped on judgement rather than on capability.

    The release builds correctly: 68,085 membership rows over 7,912 genes, 97
    studies, 51 with a confirmed permissive licence and 46 withheld. That part
    is derived facts and is safe to publish.

    But what this task asked for is different, and the two conflict. Making the
    twelve unfetchable entries downloadable means mirroring the RAW third-party
    supplements -- which is exactly what hf_publish is written to refuse:
    "Only derived facts are redistributed here ... their raw files are not
    mirrored." Publishing them would redistribute other people's copyrighted
    files under this project's name.

    So the honest options are:
      1. publish only the derived release (safe, already staged, does NOT make
         the twelve fetchable)
      2. publish the raw tree for the subset whose licence is positively
         confirmed permissive, and leave the rest unfetchable
      3. publish the raw tree entirely, accepting the redistribution

    That is the author's call, not a session's. Everything up to the upload is
    done and the command is one line: hf_publish.upload(repo_id, out_dir).

CHECKSUMS ADDED -- 2026-08-12
    Every download records a SHA-256, its size and its filename into
    checksums.json beside the dataset tree, and every later fetch checks the
    cached copy against it. A mismatch is reported with what to do about it
    rather than absorbed.

    Recorded only AFTER the content is accepted as a file rather than as an HTML
    error page: pinned before that, the first bad download becomes the truth
    every good one after it is measured against. An unpinned file is not a
    failure -- most of this tree predates checksums -- so it is pinned silently
    and checked from then on. The digest streams, because some deposits are
    gigabytes.
